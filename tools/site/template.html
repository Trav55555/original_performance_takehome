Summary

A search-based compiler produces a kernel that runs the benchmark in 975 cycles. The recorded scalar baseline takes 147,734 cycles. The compiler calls no solver. Two isolated rebuilds from source alone reproduced the same program digest, and a proof with the Z3 satisfiability-modulo-theories (SMT) solver shows the emitted program matches the reference for every tree and input value on the benchmark shape, with traversals starting at the root.

Nobody has shown that 975 cycles is optimal. The program's 5,800 vector operations need at least 967 cycles on six vector slots, but that bound ignores dependencies.

1Problem

The benchmark walks a height-10 tree of 2,047 nodes. A batch of 256 inputs takes 16 rounds. In each round, every input hashes its value with the current node's value, then moves to a child chosen by the hash. After a leaf it returns to the root.

The kernel runs on one core of a simulated very long instruction word (VLIW) machine with eight-lane single-instruction, multiple-data (SIMD) vector units. Each cycle issues one bundle. Every instruction in a bundle reads the state from the start of the cycle, and writes land at the end.

2Method

The compiler searches over two choices: cache sites, which serve tree lookups from scratch instead of gathering them from memory, and selectors to move from the flow engine to vector arithmetic. For each candidate it builds a graph, schedules it backward and then forward, and allocates scratch afresh. The forward pass tries three priority orders; one promotes the ancestors of the first 26 gathers. On the best schedule, the compiler tries final-hash rewrites on the two blocks that finish last.

Removing instructions from one engine often adds contention on another. Caching trades gathers for selection work, and arithmetic selectors move work from flow to vector arithmetic. Only the complete schedule shows whether a change helps.

3Results

The verified build scored 1,963 candidates out of a budget of 4,096. A cold build took 15 to 16 minutes, because every new process searches again; a second build in the same process took about 4 ms. The emitted kernel does not use Z3.

4Verification

The verifiers built the kernel through the public KernelBuilder and ran the nine frozen submission tests, 100 generated inputs, 100 full-width inputs, five asymmetric patterns and nine other root-starting shapes. They checked lane ownership, dependencies, scratch limits and fallbacks, and rejected executed controls at 980, 1,041, 1,042, 1,052, 1,076 and 1,082 cycles. Two source-only rebuilds at hash seeds 0 and 17 reproduced the program digest.

5Limitations

  • The kernel assumes traversals start at the root.
  • It writes final values and leaves every other memory word unchanged, but it does not write final indices.
  • The checks, including the proof, do not cover non-root starts or arbitrary dimensions.
  • Optimality is unproven. An exact search for 979 cycles on an older graph ran out of its 2 GiB memory cap after 16 hours 52 minutes.

6Context

Anthropic's original take-home allowed four hours. After Claude Opus 4 beat most human results, Anthropic switched to a two-hour version that started at 18,532 cycles. This repository uses that version's tools, with the starter code reset to the slow baseline. Table 1 lists the results Anthropic reported from the 18,532-cycle start. 7Reproduce

Caution: do not modify tests/ or problem.py. Anthropic reported that every first-day submission below 1,300 cycles was invalid because the agents had edited the tests.

Clone the repository, install requirements.txt in a virtual environment and run python tests/submission_tests.py with assertions enabled. Run git diff 5452f74 -- tests/ problem.py and confirm it prints nothing. The build and verification procedure lists the supplementary checks, including python scripts/verify_equivalence.py.
